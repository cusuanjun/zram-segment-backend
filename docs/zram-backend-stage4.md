# 第四阶段：有限输入分组、复用写缓冲与段尾拆批

状态：后端内部 API 已修改。主机打包算法测试通过；没有完整内核编译、KUnit
运行或设备验证。没有启用真实 App 识别、自动下沉、F2FS 保留区或 UFS I/O。

## 本阶段边界
输入仍是调用者持有的稳定快照。新增接口处理一次最多 64 条的有限窗口：
- 可以混合 owner，按完整 id/generation 分组。
- 按 owner 首次出现顺序处理组，组内保持原输入顺序。
- 不建立长期候选队列，不自动扫描 slot，不等待定时器。
- 不允许单条记录跨 segment；允许跨内存页和逻辑块。
- App 身份仍来自显式输入；真实 memcg provider/登记来源待确认。

## 写缓冲
配置 segment 时，预分配每设备一个共享写缓冲：
min(segment_bytes, min(64, BIO_MAX_VECS) * PAGE_SIZE)。
这是当前开发阶段的明确策略上限，不是手机配置常量，也不是每 App 一份。
配置分配失败返回 ENOMEM，清理段表，保持未配置状态；允许重试。
销毁设备时释放。逐次写入不再分配 payload 打包页。
提交时仅使用本次 io_bytes 覆盖的页面，不提交整个缓冲容量。
每次写入都重新清零有效字节后的对齐填充，避免跨 App 残留泄漏。
缓冲中未提交的旧字节不会被写入新记录范围。

不声称写入路径无分配：记录元数据、真实 BIO 仍需分配；读缓冲仍按需分配。
输入独立快照也仍由调用者提供；本阶段没有实现从 zsmalloc 直接装填最终缓冲。
未来 slot 接入时需要解决这项重复复制及稳定性问题。

## 两种接口
write_batch 保留单 owner、单次 I/O、单 segment 的语义；
超过共享缓冲容量返回 E2BIG；失败不返回本次记录的 ID。
write_records 允许混合 owner，自动形成多个单 owner 批次：
1. 完整检查所有输入，未知 owner、非法长度/格式直接拒绝，尚不发 I/O。
2. 找到能容纳当前 owner 下一条记录的旧 OPEN 段；否则分配空段。
3. 按段尾剩余容量和缓冲容量逐条装入，尾部对齐后也必须放得下。
4. 提交本批，成功后按原输入下标返回 ID。
5. 继续该 owner 的余下记录，最后处理其他 owner。

示例（4 KiB 页/块，仅教学假设）：
旧段剩余 4096 B，A 的记录为 1200/1800/1600 B。
前两条打包为 3000 B，补 1096 B 后填满旧段。
第三条在另一个段中继续，与本窗口后续 A 记录打包。
算法保持 owner 内输入顺序，不做任意重排/最优装箱。

## 部分成功
write_records 的失败不能当成整窗口回滚：
输入 [A1, B1, A2]，A 组成功后 B 组失败时，结果可能是 [id1, 0, id2]。
非零 ID 都是调用者负责安装到 slot 或 release 的有效后端记录；
零 ID 对应未发布的记录，原 zRAM 内容必须保留。
只重试失败/未处理记录，不能无条件重试整个窗口造成重复副本。
第一处准备、空间或 I/O 错误会停止余下处理；之前成功的批次不回滚。
write_records 成功仍不代表 zRAM slot 已交接，更不保证掉电持久性。

## 段尾与空间统计
旧版“为同 owner 开新段时封闭所有旧尾段”的策略已移除。
只有追加尾指针达到段容量才封闭；没装下当前记录的旧尾部保持 OPEN，
可以供之后较小的同 owner 记录使用。可能存在多个同 owner OPEN 段。
写失败仍隔离本批已预留范围；有旧有效记录时不回退尾指针。
空段且 I/O 结束后可回收，旧 owner 的其他尾段不受影响。
新增统计：
- open_tail_bytes：已归属且 OPEN 的段中尚未写入的字节，不包含 FREE 段。
- write_buffer_bytes：写缓冲 payload 页容量，不包括页指针数组、记录对象等。
原有效/失效/填充/失败字节统计继续保留；未实现有效记录迁移 GC。

## 验证
新增五组 KUnit 测试：
- 混合输入 A/B/A 按 owner 打包、ID 原下标、共享缓冲页复用、跨 App padding 清零。
- 利用旧段尾部拆分窗口。
- 旧单批接口开新段后，旧尾部仍可放入小批。
- 后续 owner 的 I/O 失败保留前组非连续成功 ID，失败记录可单独重试。
- 非法尾记录导致整个窗口预检失败不发 I/O；两段耗尽时保留八条成功记录。

运行 tools/testing/zram_backend_plan_test.py：
直接从 zram_backend.c 提取 same_owner/plan_batch，使用主机 GCC 和 UBSan 执行。
通过针对性示例及 36,000 个有限输入窗口：
4/16/64 KiB 页大小示例，512 B 至对应页大小的二次幂对齐，不同 owner/代次，
容量限制、单 owner 有序装填、每条恰好处理一次。
此测试不编译整个驱动，不验证内核 API/锁/内存分配/BIO/失败回滚。
KUnit 尚未执行，必须在配套内核复核。
