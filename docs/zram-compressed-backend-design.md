# zRAM 压缩后端第一版设计草案

状态：初始设计草案；实现进度见 zram-backend-stage1.md 与 zram-backend-stage2.md。除已确认需求和明确落实的策略外，其余仍为建议。
源码基线：685988eb2d82dc3480f665aa98b1875bf75a2b0d（baseline-original）。
本次仅添加文档，不修改现有读写行为。

## 1. 已确认的需求与边界

- 保留 zRAM：原始匿名页 → zRAM 压缩对象 → 保持压缩形态写入后端 → 读取并解压。
- 在专用后端逻辑地址范围内划分固定大小 segment；不同 App 使用不同 segment。
- 一个 App 可占多个 segment；这是逻辑布局隔离，不是 NAND 物理隔离或安全隔离。
- 段内顺序追加变长记录，记录允许跨页。失效记录造成空洞，变长追加本身不必然造成空洞。
- 软件 GC 搬迁有效记录、更新位置映射、回收旧段，与 UFS 内部 GC 不同。
- swap-in 不自动等于后端记录失效；释放须遵循实际槽位生命周期与副本策略。
- 目标设备、内核配置、PAGE_SIZE、CPU/EH 压缩路径尚未确定。
- App 的实际识别方式和信息来源尚未确定，不能把 current/PID/UID 直接当作既定方案。
- 不修改 UFS 固件；通常复用块层和 UFS 驱动。
- 本地暂不构建或运行；小批次交由学长在匹配环境编译。编译通过不等于运行正确。

## 2. 当前代码与改动边界

当前 writeback_store() 使用 zram_bvec_read() 恢复原始页，按 PAGE_SIZE 写后端，
随后清理旧压缩对象，将槽位标为 ZRAM_WB，以 element 保存后端块号。
alloc_block_bdev()/free_block_bdev() 管理固定块位图，没有变长记录或 segment GC。

建议代码组织（文件尚未创建）：

| 位置 | 职责 |
| --- | --- |
| zram_drv.c / zram_drv.h | 槽位状态、记录引用、下沉提交、读取与释放接入、生命周期 |
| zcomp.c / zcomp.h | 安全导出压缩对象快照；从后端缓冲解压或复制原始格式 |
| zram_backend.c / zram_backend.h | 后端记录、segment 分配、I/O 打包、位置映射、失效与 GC |
| Kbuild / Kconfig / 外层构建描述 | 按实际构建目标接入；不能只假设修改 Kbuild 就足够 |
| 配套核心内核接入点 | 后续提供真实 App 归属，当前源码包不足以确定 |

新模块首先是同一驱动中的职责拆分，不要求独立 .ko。
zRAM 选择/接受下沉请求；后端模块管理记录及空间；设备只接收普通块 I/O。

## 3. 候选数据结构（概念字段，不是已冻结的 C ABI）

### 3.1 owner key

用于区分归属的内部标识，暂称 owner_id；必须具有明确的生命周期。
如果来源标识可能复用，需要生命周期编号或等效机制区分旧、新归属。
未知归属不能默默合并为一个 App；未接入真实来源时仅允许显式测试归属，
不能声称完成真实 App 隔离。

### 3.2 backend record

- 稳定引用：record_ref；可考虑受引用计数保护的描述符或 ID + generation，
  具体方案待内存开销评估。不能只保存会无保护复用的裸 ID。
- owner key：用于选择段、核验搬迁目的地。
- 当前位置：segment 引用/编号及复用代次、段内字节偏移。
- payload_len：数据实际长度；record_bytes：包含可选头部与填充的占用。
- format：压缩数据或原始页数据；具体枚举与磁盘格式未定。
- 生命周期：PREPARED → LIVE → DEAD；失败则 PREPARED → DEAD。
- 在途访问保护：读取/搬迁持有引用；DEAD 后禁止新访问，已有访问结束后才能释放资源。

zRAM 槽位持有 record_ref；GC 更换其内部位置，不要求更换槽位引用。
这些状态首先是 DRAM 元数据，不假设每项都写入 UFS。
槽位与引用如何编码、是否扩展 union 或使用旁表，要测算元数据成本后决定。

### 3.3 segment

- 段号、代次、起始逻辑字节地址、容量。
- owner key：段处于使用状态时保持单一归属。
- 状态：FREE → OPEN → SEALED → RECLAIMING → FREE。
- append_tail：已保留空间的尾部，不等于已写成功或已提交的位置。
- 统计：有效记录字节、失效/废弃字节、在途预留、填充与未使用空间。
- 段内记录枚举结构：让 GC 能找到候选记录，并重新核验当前有效性。
- 在途 I/O / 位置引用：防止段回收后仍有访问旧地址。

逻辑 LIVE 统计下降不保证空间立即可覆盖；旧读取或迁移可能仍引用旧位置。
统计应明确互斥分类，不能把正在写入的字节直接计为有效数据。

### 3.4 backend context

后端设备、段表、空闲段集合、owner 到开放段的索引、记录管理、
缓冲与 I/O 队列、GC 预留空间、停止状态和统计。
后端模块可以借用由 zRAM 持有的块设备，销毁前必须排空访问；
设备句柄所有权只能有明确的一方负责释放。

## 4. 模块接口建议

以下是语义接口，不是可直接调用的函数原型：

| 操作 | 输入/输出 | 约束 |
| --- | --- | --- |
| init / destroy | 设备、参数 → context | 校验几何与容量；退出时禁止新请求并排空 I/O/引用 |
| prepare_write | owner、format、长度 → ticket | 分配描述符和段内预留；可能睡眠，不能持槽位自旋锁调用 |
| submit_write | ticket、独立数据缓冲 → 完成结果 | 缓冲归属明确，直到完成才可释放；成功尚未发布到槽位 |
| publish | 已写成功记录 → 槽位可持有的引用 | 发布须与槽位条件提交协调；不能在自旋锁下调用睡眠路径 |
| abort | 尚未发布的 ticket | 撤销引用与预留；已写字节按分配规则废弃，不能任意回退尾指针 |
| pin / unpin | 记录与当前位置的访问引用 | 从槽位取引用要与槽位锁保护衔接；读完成后归还 |
| read | 已固定的位置、缓冲 → 数据/错误 | 校验长度、边界与格式；可能跨多个 I/O 单位 |
| invalidate | 撤销槽位对记录的逻辑持有 | 若在槽位自旋锁内调用，必须非睡眠；耗时清理延后 |
| gc | 受控回收请求 | 只在后续阶段接入，保持 owner 隔离与读取保护 |

publish/invalidate 的锁内部分应尽可能只进行有界、非睡眠的状态/引用操作。
分配、I/O、等待与耗时销毁置于锁外；不能把 prepare_write 包在槽位锁内。
具体锁顺序和引用原语必须在实现阶段逐条固定，本文不宣称协议已证明正确。

## 5. 下沉事务：何时新位置成为权威位置

1. 锁外准备有界临时快照缓冲及操作上下文。
2. 槽位锁内检查状态/归属，建立本次下沉的身份，短时映射 zsmalloc 对象，
   将内容和长度/格式复制到独立缓冲，然后解除映射、解锁。
3. 保留旧压缩对象作为当前有效存储，锁外预留后端空间并提交写入。
4. I/O 成功后重新锁槽位，核验本次操作仍对应当前内容。
5. 条件满足才安装 record_ref，切换状态并解除旧对象的持有；读者看到一致状态。
6. 写失败或复核失败：不安装新映射；清理本次临时资源和未发布记录。
   若槽位已被别的操作替换/释放，不得“恢复”旧版本或清除新操作的标记。

现有 UNDER_WB/IDLE 协议需要完整审计；不能直接认定适合新后端。
候选方案是操作 token / 槽位内容代次，需防复用、防 ABA 并处理元数据成本。
不能带着 zs_map_object 返回的映射地址等待 I/O。
I/O 完成不等于映射已提交，也不自动等于掉电持久性保证。

## 6. 读取、覆盖与释放

读取：槽位锁内识别后端态并取得安全引用 → 锁外固定当前位置并读取 →
校验格式、解压/复制原始格式 → 检查完成状态 → 完成上层请求 → 释放引用。
不能在解锁后重新读取一个可能已变化的槽位 element。
压缩器输入对齐和执行上下文必须兼容 CPU/EH；不能假设任意 bio 完成上下文都能解压。

覆盖/释放：在槽位同步保护下移除对旧记录的引用，让旧记录不再服务新查询；
后端延后清理，直到旧访问结束。不得简单地因一次 swap-in 就失效。
现有 swap_slot_free_notify() 的 trylock 失败路径不能遗漏，也不能假设释放总是立即发生。

## 7. 变长打包：实现前必须解决的关键点

- byte offset、Linux bio 的 512 B sector 单位、设备逻辑块大小和 PAGE_SIZE 是不同概念。
- segment 起点/长度应满足实际 I/O 对齐要求；读取用覆盖记录的对齐范围提取 payload。
- 单条记录可以跨页；记录的长度不等于提交给块设备的 I/O 长度。
- 不能为每条记录简单向上取整至整页并宣称紧凑存储。
- 两条记录共享一个 I/O 单位时，后续写入不得覆盖已提交数据。

候选方式：按 owner/开放段维护有界打包缓冲，将多个记录合并到对齐 I/O 单位后提交。
必须进一步决定：缓冲何时封闭、批量写回怎样推进、低流量如何 flush、
尾部填充计费、写失败如何影响整批记录、何时允许各槽位发布。
不能一边等首条记录完成，一边要求下一条记录加入同一个批次才能提交，形成等待闭环。
第一版可封闭并填充不足的 I/O 尾部；已发布块不再追加改写。
这会产生明确计费的尾部浪费，不把它与记录失效空洞混为一谈。
以上策略未冻结；在接入真实写出前需形成可执行的打包与提交方案。

## 8. GC 后续阶段

选 SEALED 段 → 枚举并核验有效记录 → 为同 owner 保留目的空间 →
复制压缩记录 → I/O 成功后条件更新 record 的位置 → 延迟释放旧位置 →
所有记录处理完成且旧访问结束后，整段进入 FREE。

并发读取可继续持有旧位置；并发失效不能被 GC 重新发布。
段代次或等效保护防止旧操作访问复用后的段。
需要专用空间预留或等效进展机制，不能把所有空间用满再试图搬迁。
discard 为独立策略；必须确保范围没有有效/在途访问，并防止与重新分配竞争。
软件回收不意味着立即物理擦除。

## 9. 建议实施范围与未决项

建议第一版：运行期后端，不提供重启后恢复；沿用显式 writeback 触发；
SAME 页继续留在原有表示，原始大小数据可用 RAW 格式表示。
这些是待讨论建议，不是用户已确认的特殊情况策略。

必须逐步确认：
- 设备构建目标、配置、核心内核版本和压缩器约束。
- App 身份来源、复用生命周期、未知归属处理。
- segment 大小、打包/flush 策略、记录格式、记录引用实现。
- 上述 SAME/RAW 与重启恢复范围。
- 选择新后端的方式及与旧 WB 状态的区别；不能让旧块号被误解释成新记录引用。
- 增加的元数据、缓冲与预留内存上限。仅增加后端空间不会自动扩大 zRAM 逻辑槽位数。

A. 完成本文与关键未决项；确认接口所有权和锁顺序。
B. 增加后端骨架及初始化/销毁，不切换现有写回；提交给学长编译。

E. 接入真实 App 来源及 GC，验证生命周期和并发。

检查重点：
跨页记录、原始大小记录、写失败、读取失败、槽位覆盖/复用、
并发读与 GC、记录释放、近满空间、reset 排空、配置关闭下的构建。
读回内容应逐字节一致。编译和运行验证结果都须如实标注；
不得把没有运行的场景记为通过。
